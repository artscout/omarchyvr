What went well

Safety held

No sudo by agents, every root step through pkexec, no VR session touched, snapshots before the root jobs and home backups before the uninstall. Every step was reversible.

The NVIDIA part worked first time

Patch, dkms, boot image and the merged_head_sync check passed at 12:38; the later runs said "already patched ... nothing to rebuild". The root job is idempotent, so re-running it was safe.

Fast fixes, each with a test

Leftover NVIDIA patches (d8f80b3), EDID inside the root job (6698c18), "Which headset" + sleeping signature (6d5d20e), quickshell as the password agent (931ba25), the doctor's Monado path (4a971f8), the wake guide and window recovery (2740472).

The logs were enough

Job files with exact commands, the keepalive's journal, the kernel's USB lines and pkexec's journal lines reconstructed every minute of the day without guessing.

Decisions recorded

The user's decisions (the power-cable last resort, the base eye list, AI set-up counts as answered) went into ai/CLAUDE.md, lessons 37-40 and the docs the same day.

Downloads and keys survived

AI models, backgrounds, speech models and ai.toml were kept by both uninstalls and reused by every install.

What went wrong, and why

1. The headset sat four hours without a host

Root cause: the system part (which installs the access rule) was split from ./install.sh by hours of feature work. Without the rule the keepalive cannot open the headset; without a heartbeat the control chip restarts every ~5.4 s and after hours switched off for good. A PC restart, the power button and wearing it did not help; only the power cable did.

Evidence: 2,200 enumerations 08:34-11:51; keepalive "Permission denied" from 09:55; "waiting for headset" 12:19-13:00.

Now: the setup lists the headset's parts and shows the guide (lesson 42). Rule: one sitting for a reinstall.

2. The setup ran with the headset off

Root cause: nothing checked that the control chip was on before the system part; the EDID step needs the awake headset. Result: EDID skipped in both full runs, three EDID-only prompts that could not succeed (two exit 3, one cut by a reboot), and a problem screen without a Restart button, so the stage was edited by hand and the PC rebooted while a root job was still waiting.

Now: the EDID Fix waits (no password) while the chip is off; Restart now stays on the problem screen; the guide re-checks by itself.

3. "Ready" without the headset's parts

Root cause: the setup's checks covered the PC (driver, rule, permission) but not the headset's cameras or eye tracker, so it could call the PC ready while Work could not start.

Now: headset-camera (one restart) and eye-chip (the captured enable, once) are setup items; not Ready while missing.

4. The camera recovery made it worse

Root cause: the recovery stopped the keepalive for its whole 150 s wait. Without a heartbeat the headset cycled every 6 s and never brought its USB3 side back; then a second reset; then advice to reboot (which does not help) and to "power-cycle the link box".

Now: one restart per start, keepalive back the moment the headset leaves USB, 60 s, then the plain hint and the guide (lesson 44).

5. Every reinstall dropped the realtime permission

Root cause: lab-data.sh link re-created its symlinks on every install; the build scripts' rerun-if-changed on those directories rebuilt pimax-cam and pimax-eye, ninja relinked monado-service and the kernel cleared its file capability. The password then came at the Work start, not at the install.

Now: idempotent links, the old inode kept for identical bytes, a post-install check with the one-password Fix (lesson 43).

6. Twelve password prompts

Root causes: the udev trigger missed the eye tracker (second prompt); two Fix buttons asked separately 4 s apart; EDID Fixes while the headset was off; a Fix of the old app on a stale path; the relink of item 5; one mistyped password.

Now: the trigger covers every device of the rule; only "Fix all" with two root problems; the EDID hold; the relink guard (lesson 46).

7. Factory calibration lost

Root cause: the uninstall treated headset-calibration.xml (device data read once from the headset) as a setting and removed it; nothing re-read it, and the start showed only "omarchyvr-slam export: no calibration file found".

TODO owned by a separate change: keep it like ai.toml, read it in the setup, say it in plain words (lesson 49).

8. Tests looked like crashes

Root cause: the supervisor test crashes a window process on purpose (a null write, c7 00 01 00 00 00 at window::test_crash, window.rs:355): four kernel lines per run named omarchyvr-app. Another test aborted a sleep stand-in: 18 core dumps and "Process crashed" notifications.

Now: the crash thread is named ovr-test-crash; the stand-in ends without a core (lesson 47). Proven: the same bytes at the crash offset in the test binaries, addr2line gives omarchyvr_app::window::test_crash.

9. The eye tracker taken for a fault

Root cause: the preflight's yellow "not enumerated ... start without eye tracking" after a headset restart, where an off eye module is normal and the session switches it on.

Now: an info line "switched on at the start" (lesson 45).

10. A 2.5 GB "settings" backup

Root cause: the uninstaller put all of ~/.cache/omarchyvr into the settings tar, including the build cache; the next install then rebuilt Basalt.

Now: the build cache is removed as a cache, never tarred (lesson 48).

11. The window did not show at login

Root cause: the window process ran but had no Wayland window at autostart (12:49, 13:06); a second start only said "already runs".

Fixed in 2740472 (window ack and raise watchdog, lesson 40).

12. Lost logs

Root cause: the output of both uninstalls was kept in /tmp (the session's scratch directory) and was gone after the reboot: this retro could not read what uninstall #2 did.

Rule: keep run logs in the home directory (as the install logs were); TODO: the scripts write their own.

The flow we missed

  • A headset gate before the system part. The control chip must be on (green tick) before the job that needs the headset's display. The setup's "Get ready" card had no live state until 13:16; the job ran with the chip off.
  • One sitting. Uninstall, reboot, install, the setup's one password, one reboot, Play. Today the reinstall was interleaved with feature work and six installs of a moving main.
  • A check after every update. A changed Monado loses its permission; nobody looked until the Work start asked for a password.
  • The headset's parts as part of "ready": control chip, cameras, eye tracker, and the factory calibration.
  • Device data is not a setting. The factory calibration must survive an uninstall or be read back by the setup.
  • Read before you act. The eye power-on code and the reset's keepalive handling were in the repository; the analysis note reset-headset-slow-reenum.md had already named "keep the keepalive running" as the next suspect.

The correct flow for next time

From a working install to a clean reinstall and back to Play: one password per job, two reboots, no hand edits.

  1. Before (no VR session): back up the private .claude/, the home settings and the factory calibration; freeze main (no merges) until Play works again.
  2. Uninstall from the app or ./uninstall.sh: one password; downloads, keys and device data stay; its log goes to ~/. Reboot 1.
  3. ./install.sh (no password). It ends by opening the app. Continue at once: from now until the setup's password the headset has no keepalive.
  4. App: "Which headset do you have?", then "Get the headset ready" until the control chip shows green. If it does not: the power button (90 s), then, only as the last step and never during a session, the power cable for 10 s.
  5. The setup runs by itself: fixes without a password (keep-alive, one headset restart for missing cameras, the eye module's enable), then ONE password for the system part, then the checks again, the headset's parts included. A problem shows its one Fix ("Fix all" for several root fixes); missing parts show the guide, which re-checks by itself.
  6. Restart now in the app (reboot 2), never by hand while a password job runs. The app opens at login and finishes the checks by itself.
  7. Ready: Play or Work. Later updates: ./install.sh; an unchanged Monado keeps its permission; the app checks once and asks for one password only when Monado really changed.

How we worked: the process side

Missed verifications

  • "Install #1 worked" was reported while its system part had not run; the headset then waited hours without a host.
  • A fix committed at 13:12 was relied on at 13:18 by an app that did not have it yet.
  • The 13:07 recovery's output was not read for what it showed: one command, then 24 re-enumerations without a keepalive.

Wrong assumptions

  • "A reboot brings the chip back" (12:46: it did not).
  • "Restart headset brings the cameras back" (it made it worse with the keepalive stopped).
  • "The eye tracker is broken" (it is off by design after a restart).
  • "Monado unchanged keeps the permission" (the relink happened anyway).
  • "The uninstall only resets settings" (it removed the factory calibration).

Stale plans, hand edits

  • install.sh's plan was written with the headset asleep (fixed by rewriting it before the password).
  • The next-step note changed mid-run (automatic onboarding) while the machine stayed half installed.
  • Three hand edits: the NVIDIA restore script, setup_stage = restart, the calibration copy. Each is a missing button.

Too many restarts and installs

  • Three reboots; the one at 12:46 changed nothing (chip still off) and cut a root job.
  • Six installs: every merge to main was installed again during the reinstall.
  • Two uninstalls on one day, the second three hours after the first, with no system part in between.

Agents

  • Parallel feature agents committed and merged while the reinstall ran.
  • Their tests produced crash lines and core dumps on the user's machine.
  • A test agent repeated its reports; one report named the wrong branch (reported by the main thread).

Process rules

  1. Reinstall drills in one sitting, main frozen, the headset awake before the system part. No feature work in between.
  2. Count prompts and reboots per run and write a short timeline while working. More than one password per job or one reboot per job is a bug to file.
  3. Never edit app state by hand (gui-state.toml, setup stage, device files). If you need to, the app is missing a button: add it.
  4. "Done" means installed and seen working. Reports say "committed abc1234" or "installed at 13:22", never both loosely.
  5. Never reboot while a password job runs. Use the app's Restart now; it waits for jobs.
  6. Read the code and the logs before calling hardware broken, and before repeating a recovery that just failed.
  7. Crash triage starts with the test binaries: same bytes at the offset (od), addr2line. Tests never leave real-looking crashes.
  8. Run logs go to the home directory, never only to /tmp (lost at the reboot).
  9. Agent reports take the branch and commit from the repository's own output, are not copied from an earlier report, and the main thread checks one claim with one command before relaying it.
