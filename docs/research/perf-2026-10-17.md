# Play felt slow and the controllers tilted (2026-10-17, 14:43-14:56)

User report, in the headset: "The controllers are still a little bit tilted forwards; we fixed that before" and "the
fastness is really bad, check optimization and why we have so low". The session: Play (`omarchyvr vr start --fps 72
--6dof --ctrl-track --no-eye --light`), first with SteamVR (14:43-14:47, Half-Life: Alyx loading, SteamVR Home),
then Monado + xrizer (14:48-14:56, Half-Life: Alyx aborted in xrizer, `GetPosesForFrame` is `todo!()`). All evidence
below was read while the session ran, read only (no IPC, no restart).

## 1. What the numbers say

| Source | Window | Result |
|---|---|---|
| SteamVR `vrcompositor.txt` `Total` line | 14:43:17-14:46:28 (SteamVR Home, dashboard) | 7577 presents, **5610 dropped** (74 %). Presents + dropped = 13187 in 190 s = 69.4 per second: the compositor ran on the 72 Hz vsync but reached only ~40 fps |
| same | 14:46:28-14:47:14 (game loading) | 2846 presents, 7 dropped |
| same | 13:41 (72 Hz), 2026-10-16 21:16 (90 Hz) | 2107 / 7 and 1795 / 7: fine |
| Monado's own compositor (`omarchyvr-perf.stats`) | 14:48-14:56 (xrizer) | 18078 frames, `comp_skipped` 12, `comp_late` 22 (0.07 %): fine |
| `monado.log` "miss/late/drop" lines | 14:48- | not frame drops: they are the SLAM still gate ("re-zeroed while still ... no dropout") and "0 untimed frames skipped" |

So the slow part was SteamVR's compositor during 14:43-14:46. Monado's compositor kept up.

## 2. Causes, ranked

1. **Other work on the PC during the session (agents' builds and tests).** cargo target dirs were written 14:30-14:51
   (`rust/target-test` 14:42-14:43, `rust/target-test-wayvr` 14:39-14:42, a worktree's target 14:41-14:51 with 5737
   files at 14:48), and the app's crash-supervisor test printed four `ovr-test-crash` segfault lines at 14:50 (a test
   run, not a crash). The same thing dropped 8 % of frames on 2026-10-16 (LESSONS, memory "no GPU load during VR").
   The rule existed only as text. **Fixed**: section 3.
2. **Steam's client UI crashing in a loop while SteamVR started.** Steam was started by Play at 14:43:00; its web
   helper crashed and wrote minidumps 14:43-14:47 (`steamwebhelper` segfault in libc 14:47:15), and SteamVR's
   compositor destroyed and re-created the Steam desktop overlay (`valve.steam.desktop`) **74 times in the minute
   14:44**, plus `SharedResourceManager: leak summary 202 items` when it stopped. Every re-connect creates shared
   textures in the compositor. This is Steam's, not ours; it calmed down after 14:46 (the loading phase had 7 drops).
   Not fixed (outside the project). If it repeats: start Steam before Play, or let it finish starting.
3. **SteamVR Home at full panel resolution.** The scene app was SteamVR Home (`steamtours`) at 3840x3552 per eye
   (Quality, 100 %, SteamVR's own supersampling pinned to manual 100 %: correct). It is a heavy scene; with 1 and 2 on
   top it missed frames. Balanced (85 %) is the switch if a game needs headroom (docs/RENDER-QUALITY.md).
4. **72 Hz instead of 90 Hz.** The app's default is 90 Hz since the decision of 2026-10-16 ("90 Hz works; hands feel
   better"), and the CLI's default is 90. This install has `hz = 72` saved: the job log shows a start at 90 Hz at
   13:16:50 that failed on the missing headset calibration (not on the rate), and 24 s later a start at 72 Hz; from
   then on every start was 72. So 72 is a saved choice made while fixing an unrelated failure. At 72 Hz every frame
   lasts 13.9 ms instead of 11.1 ms: motion looks less smooth and the controllers lag more. **User decision**: switch
   Display > refresh back to 90 Hz (one click; not changed behind the user's back, the app keeps an explicit choice).
   Note: SteamVR's compositor logs "Updated HMD Prop_DisplayFrequency_Float to 90" at every 72 Hz start; the driver
   puts 72 back (vrserver.txt "set back to the device's 72.000008 Hz", fork fde1c578e) and the present counts above
   follow the 72 Hz vsync, so this is not a pacing bug.

Checked and **not** a cause:

* Realtime priority: `monado-service` has `cap_sys_nice=ep` and its compositor thread runs SCHED_FIFO 99.
* SLAM and controller tracking: monado-service ~62 % of one core, `pimax-ctrltrack` ~16 % (LED frame work 2-19 ms on
  its own thread, 40 ms budget at 25 LED frames/s); 32 threads available.
* Eye tracking off (`--no-eye`), Light game mode on (no wrist readout, no room anchor), no voice, AI or speech
  processes running, no WayVR in Play.
* The graphics card: no thermal or power-brake slowdown (`nvidia-smi -q -d PERFORMANCE`, counters 0 except 0.23 s
  SW power cap in total). Sunshine (the user's streaming, never stopped) used ~94 % of one CPU core: small.

## 3. Fix: no builds or tests while VR runs, in code

* `tools/vr-busy.sh`: exit 0 when no VR session runs, 1 when `monado-service`, `vrserver` or `vrcompositor` runs (says
  which, with pids). `--wait [MAX_S]` polls every 60 s. `--guard CMD` runs CMD at nice 19 when free and refuses with
  exit 75 and a plain message during a session.
* `.cargo/config.toml` (repo root, so the `rust/` workspace, `forks/wayvr` and every worktree get it): cargo's
  `rustc-wrapper` (`tools/vr-guard.sh`) and the test/run `runner` go through the guard. A `cargo build`, `cargo test`
  or `cargo run` started during a session stops before compiling or running anything; one started before a session
  stops at its next compiler call or test binary. Everything else runs at nice 19.
* `./install.sh` checks before every build step (it used to build during a session and only refuse to install).
* `OMARCHYVR_ALLOW_DURING_VR=1` skips the guard, only when the user asks for it. Tests: `tools/vr-busy-test.sh`
  (a copy of `sleep` under its own name stands in for the session, the real processes are never touched).

## 4. The controller tilt

The earlier fixes are all still there: the grip of a tracked controller is `aim * inverse(openxr_aim) * openxr_grip`
of the Quest 2 Touch model (Monado 48829f157, lab 14a53ce; `monado.log` shows `PIMAX_TOUCH_GRIP` at every start), and
SteamVR's driver (steamvr_drv) and xrizer (`oculus_touch.rs` `offset_grip_pose`) both derive the Touch raw pose with
the same `openxr_grip` numbers, so both game paths agree. The controller models after the reinstall are byte-identical
to the lab's.

What changed: `ctrltrack.log` says `calibration ... (factory extrinsics)`. The lab install loaded
`~/.config/pimax/ctrl-cam-extrinsics.json`, the camera extrinsics refit on controller poses (lab 7e9d910,
analysis/controller-6dof.md): the factory extrinsics of cameras 1, 2 and 3 are off by 0.46, 1.45 and 3.20 deg; cam 1
and cam 3 almost entirely about the body's x axis (pitch). The clean reinstall reset that file; the import that
brings it back from the backups (1509fe7) was committed at 14:42 and is not installed yet. Controllers seen by
cam 3 (right, lower) were therefore pitched by up to ~3 deg: "a little tilted".

**Fixed at the source**: the fit ships with the Dream Air reference (`rust/pimax-device/devices/dream-air/reference/
ctrl-cam-extrinsics.json`, serial and home path scrubbed, allowed by the leak scanner by path and sha256).
`extrinsics::resolve` (pimax-ctrltrack, also used by omarchyvr-anchor) takes the user's own fit, else the reference fit
when the headset's factory camera rig equals the reference's (the same headset, under its own serial or the reference
calibration), else the factory extrinsics. A clean install of this headset is right without any file of the user's.
Tests in `rust/pimax-ctrltrack/src/extrinsics.rs` (documented angles, only the reference headset, the order own >
reference > factory, `PIMAX_NO_REFERENCE`). The log line now says `extrinsics of cams [1, 2, 3] from the shipped Dream
Air reference (same headset)`.

If the controllers still look tilted after the new set is installed, the remaining knob is the aim pitch (52 deg from
one recording of how this user held them, `PIMAX_CTRLTRACK_AIM_PITCH_DEG`); a per-user slider in the app would then be
the next step (not added: no evidence yet that it is needed).

## 5. For the user

* Display > refresh rate: back to **90 Hz** (recommended; the saved 72 Hz came from a click during a failed start).
* The fixes take effect with the next install between sessions (the main thread installs).
